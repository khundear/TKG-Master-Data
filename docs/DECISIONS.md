| D-007 | 2026-11-11 | The schema is trimmed to what the two modules show today: brands, stores, material categories (Bible), units, materials, material brand usage, SKU categories, brand menu categories, selling SKUs, POS mappings, import batches and raw import rows. **Not yet built:** users/roles, revisions, change requests, approvals, audit events, entity registry, purchase items, unit conversions. Instead each record has a `status` (draft / approved / retired) and provenance columns (import batch, sheet, row). | Those tables belong with the approval workflow, which is not built and whose owners are open (IMPLEMENTATION-CONTEXT §10). | D-008 | 2026-11-11 | Material brand flags: flag 1 creates a `material_brand_usages` row with `usage = used`; flag 0 / blank creates **no row** (= not specified). `not_used` exists only for a future confirmed decision and is never written by the importer. | "FALSE = not specified, not prohibited" (CLAUDE.md, IMPLEMENTATION-CONTEXT §3, §5). |
| D-009 | 2026-11-11 | `pnpm db:import` replaces the previous **draft** snapshot of each workbook in one transaction, and refuses to run if any record of that workbook is no longer draft. Each run adds an import batch (file name + sha256) and keeps every source row as raw JSON (`import_rows`); old batches are kept as history. | Re-importing the sheets must be safe while everything is draft, and must never overwrite approved data. |
| D-010 | 2026-11-11 | SKU data is stored as the sheet has it (no cleansing, CLAUDE.md): L1/L2/L3 names and brand menu category are text on the SKU; `central_category_id` is set only when the sheet's SKU Category Code matches (empty today); `tkg_code` exists but is empty (not allocated). POS status (พร้อมขาย / งดขายชั่วคราว) lives on `pos_mappings` as a snapshot value, not on the SKU. The central category sheet is stored as a 3-level tree (values unchanged); brand menu categories stay flat, one row per sheet row. | The user has not released SKU data for cleansing. POS codes are mappings to the TKG key, never its replacement. |
| D-011 | 2026-11-11 | The Material Master Bible tree is read from row 16 up to the sheet's second table ("REVIEW QUEUE"): **21 · 101 · 22** categories. Level 2/3 parents come from sheet order and are tested against the code prefix. | `tools/export_data.py` also picks up a tertiary-remap table lower in the same sheet (it reports 39 level-3 rows). The database follows the spec's 21 · 101 · 22. |
| D-012 | 2026-11-11 | Shared code: `@tkg/ui` (React shell pieces with the prototype's CSS class names; the app passes its Link and pathname hook in through `UiProvider`), `@tkg/i18n` (`_t()`, Thai key; English in `packages/i18n/src/core.json`, `apps/web/lib/en.json`, `modules/<id>/i18n/en.json`; `pnpm check:i18n`), `@tkg/db` (`prisma`, `filters` incl. the มีหมู filter, reference constants). One `.env` at the repo root, loaded by the package scripts with dotenv-cli. | Mirrors ICW-OS-APP's `packages/ui`, `packages/i18n`, `packages/db` (PLATFORM.md) so code can be lifted later; module sessions build on one kit instead of inventing their own. |

## Open (see IMPLEMENTATION-CONTEXT.md §10)

- Material and SKU code formats, UUID policy, POS mapping per branch. (Today: UUID primary keys; `materials.code` = current Material ID; `selling_skus.master_record_key` = sheet key; `tkg_code` empty.)
- Revisions, change requests and approvals (D-007): needed before anything can become `approved`.
- Owners and approvers per data type.
- SKU cleansing and restructure — waits for the user.
